## Название

**«Норма»** (Norma) — выбрано 2026-11-16. Смысл: «твоя норма калорий», коротко,
одинаково звучит по-русски и по-английски. Каталог переименован из `MindVault` в

## Что это

Веб-приложение, которое собирает данные о повседневном образе жизни в одной
системе: питание, вес, физическая активность, цели и прогресс. Главная идея —
не «ещё один дневник калорий», а **планирование питания**: меню на день и неделю
под заданные калории и БЖУ, с отсечением аллергенов, учётом того, что есть дома, и
автоматическим списком покупок.

## Проблема

Человек худеет или набирает массу и не видит картины: калории в одном приложении,
вес в блокноте, активность в телефоне, рецепты в переписке. Цели ставятся, прогресс
не отслеживается, решение принимается по одной цифре на весах, которая скачет от воды.

## Границы с NEST (делается параллельно, руками)

NEST — бытовой органайзер (Notes, Tasks, Recipes, Finance, Dashboard, User).

| Модуль NEST | Решение |
|---|---|
| **Recipes** | Единственное пересечение. В v1 рецептов нет. В v2 рецепт — набор ингредиентов с граммовками, из которого **считается** КБЖУ (вычислимая сущность), а не текстовая библиотека. |
| Dashboard | Формально похоже, по сути разное: сводка задач и трат против здоровья. |
| Notes, Tasks, Finance | Пересечения нет. |

Архитектурно проекты тоже разные: NEST — Clean Architecture + CQRS + MediatR;
здесь — вертикальные срезы и функциональное ядро (см. ниже). Два разных подхода в
портфолио лучше, чем один дважды.

## Принципы продукта

1. **Скорость записи.** Критерий не «работает», а «записать приём пищи — до 15
   секунд». Избранное, «повторить вчерашнее» и недавние — с первого дня.
2. **Цифры объясняются.** Видно, откуда взялась целевая калорийность; никаких
   «магических» рекомендаций.
3. **Честность без медицины.** Никаких диагнозов и советов по лечению. Дисклеймер,
   выгрузка и удаление своих данных.
4. **Аллергены fail-closed.** Если данных об аллергене нет — ингредиент считается
   небезопасным. Пропустить аллерген (вред) хуже, чем не предложить блюдо
   (неудобство).
5. **Русские продукты из коробки.** Open Food Facts плюс свои продукты и правки
   поверх чужих данных (сообщество ошибается).
6. **Без ИИ внутри веб-приложения.** Вся «умность» — арифметика, статистика и
   детерминированные алгоритмы, проверяемые тестами.

## Архитектура: вертикальные срезы + функциональное ядро

- **Срезы.** Код группируется по сценариям, а не по слоям. Один сценарий — одна
  папка: HTTP-контракт, обработчик, валидация, ответ. `minimal API`, без
  контроллеров, без MediatR, без сервис-слоя «на всякий случай».
- **Функциональное ядро.** Всё, что вычисляется, — чистые функции в `Core`: без EF,
  без DI, без `DateTime.Now` и без обращений к БД; даты и «сейчас» передаются
  параметрами. Тестируется юнит-тестами за миллисекунды.
- **Правила:** срез не вызывает обработчик другого среза; бизнес-правило живёт в
  `Core`, а не в эндпоинте и не в EF-конфигурации; generic-репозиториев нет — EF
  Core и есть доступ к данным.

```
src/
  Api/           minimal API, аутентификация, склейка DI
  Features/      папка на сценарий: Foods/SearchFood, Diary/AddEntry, Weight/LogWeight,
                 Goals/SetGoal, Planner/GenerateWeek (v2)
  Core/          EnergyMath, MacroMath, TrendMath, Planner
  Data/          DbContext, EF-конфигурации, миграции
  Jobs/          фоновые задачи: импорт дампа Open Food Facts
tests/
  Core.Tests/    юнит-тесты чистых функций
  Api.Tests/     интеграционные: WebApplicationFactory + Testcontainers (Postgres)
```

## Стек

.NET 9, ASP.NET Core minimal API, PostgreSQL, EF Core, Angular + TypeScript
(Tailwind/Taiga UI по вкусу), Docker Compose, `/api/v1` с первого дня.
Многопользовательское, с изоляцией данных по `userId`. PWA — по мере готовности.

## Домен

```
Профиль        пол, возраст, рост, вес, уровень активности, цель и темп
  └─ Расчёт    BMR (Mifflin–St Jeor) → TDEE → целевые ккал и БЖУ

Продукт        название, КБЖУ на 100 г/мл, аллергены, штрихкод,
               источник (OFF | свой), пользовательские порции и правки
Приём пищи     дата, тип → позиции (продукт + граммы)
Активность     дата, тип, минуты → ккал по MET
Вес            дата, значение → тренд (EMA), скорость кг/нед, прогноз
Рецепт (v2)    ингредиенты с граммовками → КБЖУ на 100 г и на порцию
```

## Источники данных

### База продуктов: USDA + наша локализация

- **Источник:** USDA FoodData Central — лицензия CC0 (public domain), то есть
  можно свободно хранить производную базу и публиковать её в репозитории.
  Берём только generic-продукты («Foundation Foods» и «SR Legacy»), раздел Branded
  не нужен: американские бренды нам бесполезны, а базовые ингредиенты — то, из чего
  состоит домашняя еда.
- **Импорт разовый:** bulk CSV, отбор ~400–600 базовых ингредиентов.
- **Русские названия — это не перевод, а кураторство.** Записи USDA выглядят как
  «Chicken, broilers or fryers, breast, meat only, cooked, roasted», и дословный
  перевод даёт мусор. Нужно нормативное название («куриная грудка, отварная»),
  выбранное человеком. Поэтому локализация живёт **в нашей таблице**, а исходные
  данные остаются неизменными.
- **Модель:**
  - `Food` — источник, `sourceId`, КБЖУ на 100 г, состояние продукта;
  - `FoodName` — название на локали, признак основного;
  - `FoodAlias` — синонимы для поиска («гречка» → «Крупа гречневая»).
- **Состояние продукта** (сырой / варёный / жареный) — отдельное поле. КБЖУ
  отличаются кардинально: гречка сухая ~343 ккал, варёная ~110. Путаница здесь
  означает неправильные калории у пользователя, это не мелочь.
- **Проверка:** 20 позиций сверяются с независимым справочником; расхождение
  больше 10% — разбор.
- **Как делать перевод:** машинный первый проход и **обязательная вычитка
  человеком**. Использование ИИ на этапе подготовки данных допустимо (внутри
  приложения ИИ нет), но финальное название утверждает человек.

### Бренды и штрихкоды: Open Food Facts по требованию

- Дамп целиком не импортируем: ищем через API при запросе и кэшируем в локальную
  таблицу при первом обращении.
- Атрибуция «данные Open Food Facts (ODbL)» — в интерфейсе и в README.
- Правки пользователя поверх данных OFF хранятся отдельно и приоритетнее общих.

### Рецепты

- 30–50 своих seed-рецептов: ингредиенты с граммовками плюс своя короткая
  инструкция; КБЖУ считается из ингредиентов.
- Никакого скрапинга сайтов рецептов: авторские права на тексты и фото плюс
  хрупкость. Фото — свои или CC0 (Unsplash/Pexels) с атрибуцией, либо на старте без
  фото.
- «ПП» — не категория, а фильтр по вычисленным макросам (белок, калорийность на
  100 г, сахар).

## Движок (проверяется тестами, а не глазами)

- BMR/TDEE/целевая калорийность и дата достижения цели;
- активность по MET-таблицам;
- тренд веса по EMA + скорость изменения + прогноз;
- единицы измерения (г/мл/порции) и округления;
- агрегаты по дням и неделям с учётом часового пояса пользователя;
- **генератор меню (v2):** набор блюд на период, сумма КБЖУ в коридоре, аллергены
  исключены, разнообразие не ниже порога, докупки минимизированы; из меню
  выводится список покупок с агрегацией и переводом единиц;
- изоляция данных между пользователями.

## v1 — шесть задач с критериями приёмки

1. **Профиль и цель.** BMR → TDEE → целевые ккал/БЖУ. *Приёмка:* юнит-тесты на 5
   известных пар «профиль → калорийность»; в UI видно, из чего сложилась цифра.
2. **База продуктов.** Поиск по локальной БД (сид из Open Food Facts), штрихкод,
   свой продукт, правки поверх OFF сохраняются как пользовательские. *Приёмка:*
   поиск по 1000+ продуктов < 150 мс; правка OFF-продукта не портит общую запись.
3. **Дневник питания.** Добавление позиции за ≤15 секунд, «повторить вчерашнее»,
   избранное, итоги дня. *Приёмка:* дневные суммы равны сумме позиций; сценарий
   из трёх нажатий укладывается в 15 секунд.
4. **Вес и тренд.** Запись, EMA-тренд, скорость кг/нед, прогноз даты цели.
   *Приёмка:* тесты на сглаживание (шум не двигает прогноз).
5. **Активность.** MET-таблица, расчёт ккал, вклад в дневной баланс. *Приёмка:*
   тесты на 10 видов активности, отрицательных значений нет.
6. **Статистика и изоляция.** Средние по калориям и белку, отклонение от цели,
   график недели. *Приёмка:* интеграционный тест на каждый эндпоинт — A не видит
   записей B.

## Риски

1. **Трение при вводе** — главная причина смерти таких приложений.
2. **Качество данных Open Food Facts** и неполные данные об аллергенах. Лечится
   своими продуктами, правками и правилом fail-closed.
3. **Переполненный рынок.** Отличие — локализация, прозрачные расчёты, отсутствие
   подписок, выгрузка данных и планировщик меню.
4. **Расползание.** Шесть задач v1 — уже много.
5. **Алгоритм меню может не сойтись по ограничениям.** Нужен честный UI «не удалось
   уложиться, вот ближайший вариант и чего не хватило».
