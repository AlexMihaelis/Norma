# Ветки, коммиты, мерж

Коротко: **задача = ветка**, `main` всегда зелёный, мерж — только после
зелёных тестов. Правила рассчитаны на GitHub-совместимый процесс: одна задача —
одна ветка — один merge.

## Главное

- `main` собирается и проходит тесты в любой момент. Прямых коммитов в `main`
  нет — даже для опечатки в README.
- Черновик, эксперимент и недоделанное живут в ветке и в `main` не попадают.
- Одна задача — одна ветка. Не смешиваем в одной ветке «тренд веса» и «список
  покупок»: такую ветку потом невозможно ревьюить и откатывать.

## Имена ветвей

Формат: `<тип>/<область>-<кратко>`, английский, kebab-case.

| Тип | Когда | Пример |
|---|---|---|
| `feat/` | новая функциональность | `feat/core-weight-trend` |
| `fix/` | исправление поведения | `fix/api-plan-validation` |
| `docs/` | только документы и память | `docs/workflow` |
| `chore/` | инфраструктура, зависимости | `chore/ef-migrations` |
| `test/` | тесты без изменения поведения | `test/core-planner-locale` |

Области: `core`, `api`, `web`, `db`, `docs`.

Правило проверки: через полгода по имени ветки должно быть понятно, что она
делала и что в ней ломать нельзя.

## Коммиты

- Conventional Commits, английский, повелительное наклонение:
  `feat(core): calculate calorie and macro targets`.
- Один коммит — одно осмысленное изменение. Функциональность, тесты и
  документация — отдельными коммитами, даже если сделаны за один присест.
- Тело коммита — «зачем» и на что это влияет; «что» видно из diff.

## Когда задача готова

1. Сборка и тесты зелёные. Тесты в песочнице агента не запускаются — их
   прогоняет пользователь в Rider (`Run All Tests`).
2. Мерж в `main` **с merge-коммитом**, чтобы граница задачи была видна в
   истории:

   ```powershell
   git switch main
   git merge --no-ff feat/calorie-targets -m "Merge branch 'feat/calorie-targets'"
   ```

3. Удалить слитую ветку: `git branch -d feat/calorie-targets`.
4. Если тесты упали — ветка живёт, правки продолжаются в ней. В `main` не
   мержим, пока не зелено.

Альтернатива `--no-ff` — squash-мерж (`git merge --squash`). Он даёт линейную
историю, но прячет ветку. Для этого проекта выбран `--no-ff`: видно, какой
задачей и когда появился модуль.

## Удалённый репозиторий

Пока его нет — вся работа локальная. Когда появится GitHub, те же правила
превращаются в pull request: ветка пушится, PR открывается, мерж — через кнопку
«Create a merge commit». Ничего переучивать не придётся.

## Память

Договорённости о процессе дублируются одной строкой в `AGENTS.md` со ссылкой
сюда — подробности держим в этом файле, чтобы память не распухала.
