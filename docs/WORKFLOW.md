# Ветки, коммиты, мерж

Коротко: **задача = ветка**, `main` всегда зелёный, мерж — только после
зелёных тестов. Правила рассчитаны на GitHub-совместимый процесс: одна задача —
одна ветка — один merge.

## Главное

- `main` собирается и проходит тесты в любой момент. Прямых коммитов в `main`
  нет — даже для опечатки в README. Исключение одно: чистка комментариев после
  мержа блока задач (см. ниже).
- Черновик, эксперимент и недоделанное живут в ветке и в `main` не попадают.
- Одна задача — одна ветка. Не смешиваем в одной ветке «тренд веса» и «список
  покупок»: такую ветку потом невозможно ревьюить и откатывать.

## Имена ветвей

Формат: `<тип>/<область>-<кратко>`, английский, kebab-case.

| Тип | Когда | Пример |
|---|---|---|
| `feat/` | новая функциональность | `feat/core-weight-trend` |
| `fix/` | исправление поведения | `fix/api-plan-validation` |
| `docs/` | только документы и память | `docs/workflow` |
| `chore/` | инфраструктура, зависимости | `chore/ef-migrations` |
| `test/` | тесты без изменения поведения | `test/core-planner-locale` |

Области: `core`, `api`, `web`, `db`, `docs`.

Правило проверки: через полгода по имени ветки должно быть понятно, что она
делала и что в ней ломать нельзя.

## Коммиты

- Префикс — Conventional Commits латиницей: `feat(core):`, `fix(api):`, `docs:`,
  `chore:`.
- Описание после префикса — по-русски, кратко, действие плюс объект в родительном
  падеже: `feat(core): добавление расчета нормы калорий и БЖУ`.
- Без буквы «ё» — только «е» (расчет, а не расчёт). Без длинного тире — только
  дефис `-`.
- Один коммит — одно осмысленное изменение. Функциональность, тесты и
  документация — отдельными коммитами, даже если сделаны за один присест.
- Тело коммита — «зачем» и на что это влияет; «что» видно из diff.

## Комментарии в коде

- В ветке задачи код идёт с подробными комментариями: короткие пояснения к
  действиям и решениям, чтобы при ревью было понятно, что и зачем. Ветка
  пушится как есть — на GitHub видно, что и зачем делалось.
- После мержа блока задач лишние комментарии чистятся отдельным коммитом в
  `main`: остаются XML-summary публичных типов и методов плюс короткие «почему»
  в неочевидных местах (безопасность, странные решения). В ветке задачи
  подробные пояснения остаются как след работы.

## Перед коммитом: остановка и разбор

Пользователь хочет видеть объяснение до коммита, а не после. Поэтому агент:

1. заканчивает код и убеждается, что сборка зелёная;
2. останавливается и пишет понятный разбор: что сделано, зачем, какие
   определения и решения стоят за кодом и на что смотреть в файлах;
3. начинает разбор с **мини конспекта**: кратко (5-10 пунктов) перечисляет
   технологии, методы и приемы, которые применены в задаче, и **объясняет
   определения использованных терминов** простыми словами - что такое срез, DTO,
   Include, уникальный индекс, конкурентность, идемпотентность и т.п. Задача
   конспекта - чтобы джун понял написанное, а не пересказать «что сделано»;
4. ждёт подтверждения пользователя;
5. только затем коммитит, пушит и мержит.

## Когда задача готова

Готовая задача не остаётся только локально: и ветка, и `main` сразу уходят в
GitHub, чтобы история была видна не только на этой машине. Ветки после мержа
сохраняются - удалять их не нужно.

1. Сборка и тесты зелёные. Тесты в песочнице агента не запускаются - их
   прогоняет пользователь в Rider (`Run All Tests`).
2. Пуш ветки, чтобы история задачи появилась на GitHub:

   ```powershell
   git push -u origin feat/calorie-targets
   ```

3. Мерж в `main` с merge-коммитом, чтобы граница задачи была видна в истории:

   ```powershell
   git switch main
   git merge --no-ff feat/calorie-targets -m "слияние ветки 'feat/calorie-targets' в 'main'"
   git push origin main
   ```

4. После мержа блока задач (не каждой отдельной задачи) — чистка лишних
   комментариев отдельным коммитом в `main` и пуш:

   ```powershell
   git commit -am "refactor(api): чистка комментариев после мержа"
   git push origin main
   ```

5. Ветку **не удаляем**: она остаётся и локально, и на GitHub как след задачи -
   видно, в какой ветке работа велась и когда она вошла в `main`.
6. Если тесты упали - ветка живёт, правки продолжаются в ней. В `main` не
   мержим, пока не зелено.

Альтернатива `--no-ff` — squash-мерж (`git merge --squash`). Он даёт линейную
историю, но прячет ветку. Для этого проекта выбран `--no-ff`: видно, какой
задачей и когда появился модуль.

## Удалённый репозиторий

Репозиторий: `https://github.com/AlexMihaelis/Norma`, remote `origin` — SSH.

- Ветка пушится, как только задача готова (шаг 2 выше), - на GitHub видна вся
  работа, а не только итоговый merge.
- На GitHub можно открыть PR, мерж - кнопкой «Create a merge commit» (тот же
  `--no-ff`, граница задачи видна и в GitHub, и локально).
- После мержа локально: `git switch main && git pull --ff-only`.

Особенность этой машины: HTTPS сломан (schannel не может получить учётные данные),
поэтому весь обмен идёт по SSH. В песочнице агента git запускает `ssh.exe`
напрямую через `core.sshCommand` — если оставить оболочку, `sh.exe` не может
создать служебный канал и пуш падает. Ключ хоста лежит в `~/.ssh/known_hosts`.

## Память

Договорённости о процессе дублируются одной строкой в `AGENTS.md` со ссылкой
сюда — подробности держим в этом файле, чтобы память не распухала.
